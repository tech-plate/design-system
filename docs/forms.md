# フォーム

入力フォームの組み立て方。**1項目の構造を固定し、画面ごとに作り直さない。**

文言の書き方は [writing.md](./writing.md)、余白の値は [spacing.md](./spacing.md)、
色は [color.md](./color.md)、ボタンは [components.md](./components.md) を参照。

## 1. 1項目の構造（これが正）

**ラベル → 入力 → 説明文 → エラー** の縦並びで固定する。この順序と余白を変えない。

```tsx
/** フォームの1項目。プロダクト内で必ずこれを経由し、画面ごとに組み直さない */
export function Field({
  label,
  required,
  error,
  description,
  children,
}: {
  label: string;
  required?: boolean;
  error?: string;
  description?: string;
  children: React.ReactNode;
}) {
  return (
    <div className="space-y-2">
      <Label>
        {label}
        {required && <span className="ml-0.5 text-destructive-text">*</span>}
      </Label>
      {children}
      {description && <p className="text-sm text-muted-foreground">{description}</p>}
      {error && <p className="text-sm text-destructive-text">{error}</p>}
    </div>
  );
}
```

| 要素 | 規定 |
|---|---|
| ラベル位置 | **入力の上**。横並び（左ラベル）にしない |
| 必須マーク | ラベル直後の `*`（§3） |
| 説明文 | 入力の**下**。補足情報なので、入力を妨げない位置に置く（§4） |
| エラー | 入力の**下**。`text-sm text-destructive-text` |
| 入力欄の文字 | **`text-base`（16px）固定**。iOS は 16px 未満の入力欄にフォーカスすると画面を拡大する（[typography.md](./typography.md)） |
| 項目内の余白 | `space-y-2`（8px） |
| 項目どうしの余白 | `space-y-4`（16px） |

> 余白は [spacing.md](./spacing.md) §1 の段から選ぶ。
> `space-y-1.5`（6px）のようなスケール外の値を使わない。

## 2. レイアウト

- **1カラム**。入力を横に並べない
- 入力欄は `w-full`。フォーム全体を `max-w-*` で絞って行長を抑える
- **例外**: 桁数が決まっていて短い入力（年・月・郵便番号・時刻）は、個別に幅を指定してよい。
  フル幅にすると入力できる量を誤認させるため
- 項目数が多いときは**セクションに分ける**（見出し + `space-y-6`）。タブで分けるのは、
  片方だけ保存できる場合に限る（保存境界とタブ境界を一致させる）

### 2-1. 2カラムにしない

「氏名（姓）｜氏名（名）」のような**1つの概念を分割した入力だけ**横並びを許す。
無関係な項目を詰めるために横に並べない（視線が Z 字に動き、入力順が壊れる）。

## 3. 必須は `*` で示す

- **必須の項目に `*` を付ける。**「（任意）」は使わない
- 色は `text-destructive-text`。`text-destructive` は面用のトークンで白地に載せると
  コントラストが足りない（[color.md](./color.md) §1-3）
- フォーム冒頭に「\* は必須項目です」の凡例を置いてよい（置かなくてもよい）

> **`*` と「必須」と「（任意）」を混在させない。** 同じフォーム内で3通りの表現が出ると、
> 印の有無が何を意味するのか読み取れなくなる。

## 4. ラベルと説明文

- **ラベルは名詞句**。動詞を付けない（[writing.md](./writing.md) §1）
- **説明文はラベルから読み取れないことだけ**書く。言い換えしか書けないなら書かない（同 §2）
- **説明文は入力の下に置く**。あくまで補足情報であり、入力の開始を妨げない
- **入力形式は説明文ではなくプレースホルダの入力例で示す**（同 §3）。
  説明文は下にあるため、打ち終わってからでないと読まれない前提で書く
- 説明文は `aria-describedby` で入力に紐づける。DOM 上は下でも、読み上げでは
  入力にフォーカスした時点で読まれる
- **プレースホルダを説明の代用にしない**。用途は入力例だけ（同 §3）

```tsx
// NG: プレースホルダがラベルの繰り返しで、形式が何も伝わらない
<Field label="営業時間" description="営業時間を設定します。">
  <Input placeholder="営業時間を入力..." />
</Field>

// OK: 形式はプレースホルダの入力例で示し、説明文には補足だけを書く
<Field label="営業時間" description="全曜日共通です。24 時を超える場合は翌日扱いになります。">
  <Input placeholder="25:00" />
</Field>
```

## 5. エラーの表示

| 項目 | 規定 |
|---|---|
| 位置 | その入力の**すぐ下**。フォーム上部にまとめない |
| サイズ | `text-sm`（ヘルプテキストと同じ。読ませたいものを小さくしない） |
| 色 | `text-destructive-text` |
| 入力欄 | エラー時は `border-destructive` を付ける。フォーカス中のリングも `ring-destructive` にする（[components.md](./components.md) §1-1 フォーカス表示）。**色だけに頼らない**（`*` とエラー文が併存する） |
| 文言 | 次の行動を書く（[writing.md](./writing.md) §4） |

### 5-1. エラーをダイアログにまとめない

送信時に検証エラーをダイアログで一覧表示しない。**どのフィールドが悪いのか**が分からず、
閉じてから探し直すことになる。インライン表示が原則。

例外は、**単一フィールドに帰属しないエラー**（「決済合計と総売上が一致しません」のような
複数入力の整合性エラー）。この場合はフォーム先頭に `Alert` の surface variant で置く
（[components.md](./components.md)）。ダイアログではない。

### 5-2. 最初のエラーへスクロールする

送信して検証に落ちたとき、**最初のエラー項目までスクロールしてフォーカスを当てる**。
画面外でエラーが出ていると、押しても何も起きないように見える。

## 6. 検証のタイミング

**初回は送信時に検証し、一度エラーが出た項目はそれ以降 onChange で再検証する。**
react-hook-form の既定（`mode: "onSubmit"` / `reValidateMode: "onChange"`）がこの動きなので、
**`mode` を明示的に書き換えない。**

| タイミング | 可否 | 理由 |
|---|---|---|
| 送信時に検証 | ✅ 既定 | 入力途中に赤くしない |
| エラー後は入力のたびに再検証 | ✅ 既定 | 直したことがすぐ分かる |
| 入力のたびに検証（`onChange`） | ❌ | 打ち終わる前に赤くなる |
| フォーカスが外れたら検証（`onBlur`） | ❌ | タブ移動しただけで赤くなる |

サーバ側でしか判定できないもの（重複チェック等）は送信時のみ。
**クライアントとサーバで検証ルールを二重に書かない**（スキーマを共有する）。

## 7. 送信

- **送信ボタンは `LoadingButton` 等で送信中を示す**。生の `<button>` + 手動 `disabled` にしない
  （[components.md](./components.md)）
- **未入力を理由に送信ボタンを `disabled` にしない。** 押せない理由が分からず詰まる。
  押させて、エラーを出す
- 送信ボタンの行はボタン行（[components.md](./components.md) §2-3）
- **二重送信を防ぐ**。送信中はボタンを無効化する（`LoadingButton` がやる）
- 送信に成功したら、**次にどうなるかを示す**（画面遷移、またはトーストで結果を出す。トーストの仕様は [components.md](./components.md) の Toast）。
  送信の失敗・入力エラーはトーストにしない（§5）

### 7-1. 破壊的な操作は確認する

削除・取り消しなど元に戻せない送信は `ConfirmDialog` を挟む。`window.confirm()` は使わない
（[components.md](./components.md)、文言は [writing.md](./writing.md) §7）。

## 8. 入力部品の選択

| 入力するもの | 使うもの |
|---|---|
| 短いテキスト | `Input` |
| 長いテキスト | `Textarea` |
| 選択肢 2〜3 個・排他 | `RadioGroup`（開かずに全部見える） |
| 選択肢 4 個以上・排他 | `Select` |
| オン/オフ 1個 | `Switch`（即時反映）/ `Checkbox`（送信して反映） |
| 日付 | `DatePicker`。生の `type="date"` を直接置かない（§8-1） |
| 金額・数値 | 数値用の専用コンポーネント（桁区切り・IME 対策を共通化する） |

**`Switch` と `Checkbox` の使い分けは「即時反映かどうか」**。
設定画面のトグルで即保存するなら `Switch`、送信して初めて反映されるなら `Checkbox`。

### 8-1. ネイティブの日付入力をそのまま置かない

iOS Safari の `type="date"` / `type="month"` は `appearance: auto` のとき `width: 100%` を無視し、
intrinsic な幅で描画されてコンテナをはみ出す。**ページ全体が横スクロールする。**

共通の入力コンポーネント側で次を当てておく（画面ごとに対処しない）。

```css
input[type="date"],
input[type="month"] {
  -webkit-appearance: none;
  appearance: none;
  min-width: 0;
  max-width: 100%;
}
```

### 8-2. Select の矢印は部品側で置く

`Select` は既定の矢印を消して chevron を自前で置く（[components.md](./components.md) §3-1 が正）。

## 9. 共通コンポーネントに集約する

**`Field` 相当を1つ持ち、フォームは必ずそれを経由する。**
画面ごとにラベル・必須マーク・エラー文を直書きすると、余白・文字サイズ・色が必ずバラつく
（実際に、エラー文のサイズが `text-sm` と `text-xs` に割れ、色トークンも 2 種類に割れた実例がある）。

- 必須マーク・エラー・説明文の**見た目を決めるのは `Field` だけ**
- 個別フォームが `Field` に渡すのは値だけ
- `Field` で表現できない要件が出たら、**`Field` を拡張する**（迂回して直書きしない）

## 10. レビュー用チェックリスト

差分行を対象に当てる。

- [ ] 項目が `Field` 相当の共通コンポーネントを経由しているか（ラベル・エラーを直書きしていないか）
- [ ] ラベルが**入力の上**にあるか
- [ ] 必須が `*` で示されているか（「（任意）」「必須」と混在していないか）
- [ ] 説明文が**入力の下**にあるか。ラベルの言い換えになっていないか
- [ ] プレースホルダが入力例になっているか（ラベルの繰り返しでないか）
- [ ] エラーが**その入力の下**に `text-sm` で出ているか（ダイアログにまとめていないか）
- [ ] 検証タイミングを既定から変えていないか（`mode` を書き換えていないか）
- [ ] 送信ボタンを未入力で `disabled` にしていないか
- [ ] 送信中の表示があるか（二重送信を防げているか）
- [ ] 送信ボタンの行が components.md §2-3 どおりか
- [ ] 画面側の余白（フィールド間・フォームとボタン列の間）が spacing.md §1 の段から外れていないか
