# ナビゲーション

メニュー（サイドバー・グローバルナビ）の組み立て方。
**メニューはオブジェクト（名詞）で組む。** 動詞・役割・データの性質で組まない。

色は [color.md](./color.md)、余白は [spacing.md](./spacing.md)、文言の書き方は [writing.md](./writing.md) を参照。

この文書は 2 部に分かれる。

| 部 | 節 | 対象 |
|----|-----|------|
| 第 1 部 メニューの組み立て | §0〜§10 | サイドバー・グローバルナビを持つ業務画面（to B）。項目の立て方はスマホ中心の画面のタブにも当てはまる。to B のヘッダーは §9 |
| 第 2 部 スマホ中心の画面のナビ | §11〜§17 | ボトムタブバーと下層ヘッダーで組む画面（to C） |

どちらの骨格を使うかは [design.md](./design.md)、z-index・タッチターゲット・ブレークポイントの値は
[layout.md](./layout.md) が正。

# 第 1 部 メニューの組み立て

## 0. なぜオブジェクトで組むのか

メニューが読みにくくなるとき、原因はたいてい**分類軸が複数混ざっている**ことにある。
「業務か設定か」「自分のものか全体か」「admin か一般か」「マスタかトランザクションか」を
同じ階層に並べると、利用者は「探しているものがどの軸に属するか」を先に当てないと辿り着けない。

利用者が探すのは**オブジェクト**（顧客・予約・経費申請・スタッフ）であって、
そのオブジェクトの管理上の性質ではない。だから軸をオブジェクト1本に固定する。

## 1. メニュー項目はオブジェクトで立てる

**1 オブジェクト = 1 メニュー項目。同じオブジェクトを2箇所に出さない。**

| ❌ 項目として立てない | 理由 | ✅ どうするか |
|---|---|---|
| 動詞（「新規受付」「申請する」） | 操作であってオブジェクトではない | オブジェクトの画面に置く主アクション（ボタン）にする（§7） |
| 役割（「admin メニュー」「管理者向け」） | 役割は分類軸ではない（§2） | 権限で項目の表示/非表示を切る |
| データの性質（「マスタ」「トランザクション」） | 利用者の関心事ではない | 設定に属するなら「設定」へ（§3）、業務オブジェクトならトップに置く |
| 表示形式（「一覧」「カレンダー」） | 同じオブジェクトの別ビュー | 画面内のビュー切替にする |

> **同じオブジェクトが2つのグループに現れていたら、グループの切り方が間違っている。**
> 例: 「スタッフ」がシフト関連のグループと人員設定のグループの両方にある状態。
> これは「シフト」というグループがオブジェクトではなく**業務プロセス**で切られているために起きる。
> スタッフは1項目にして、シフトはスタッフ画面の中のビューにする。

## 2. 権限は分類軸ではない

**ロールごとにメニューツリーを組み替えない。** ツリーは1つで、権限は**項目の表示/非表示**にだけ効かせる。

```ts
// NG: ロールごとに別のツリーを返す。同じオブジェクトの定義が role の数だけ増殖し、
//     片方だけ項目が足される・消えるといったズレが必ず起きる
if (role === "viewer") return VIEWER_MENU;
return ADMIN_MENU;

// OK: ツリーは1つ。項目ごとに可視条件を持つ
const MENU = [
  { label: "顧客", href: "/customers" },
  { label: "売上", href: "/sales", visible: canViewSales },
];
```

### 2-1. スコープで項目を分けてよい。ただしラベルを揃える

「自分のもの」と「全体（管理側）」は**別の仕事**なので、**項目を分けてよい**。
ただし分けるなら、**同じオブジェクトであることがラベルから読み取れること**。

ルールは2つだけ:

1. **語幹（オブジェクト名）を完全に一致させる**
2. **スコープを示す接尾辞は `管理` に固定する**

| スコープ | ラベル | 例 |
|---|---|---|
| 自分のもの | オブジェクト名そのまま | `経費申請` / `支給明細` |
| 全体・管理側 | `<オブジェクト名>管理` | `経費申請管理` / `支給明細管理` |

**`一覧` を接尾辞に使わない。** 「一覧」は表示形式であってスコープではない（自分の側も一覧で表示される）。
`経費申請` と `経費申請一覧` が並んでいても、後者が「全体を管理する画面」だとは読み取れない。

**語幹をズラさない。** `支給明細`（自分）に対して `給与管理`（全体）のように語幹が変わると、
同じオブジェクトだと気づけない。`支給明細` / `支給明細管理` に揃える。

> 分けた2項目は**同じグループに隣接して置く**。離れたグループに置くと、結局ツリーが
> 役割で分断されたのと同じ状態になる。

## 3. 設定は末尾に1つ

**設定系のグループを複数作らない。** 「設定」を1つだけ置き、その中でオブジェクト別に並べる。

| ❌ | ✅ |
|---|---|
| 料金マスタ / 人員マスタ / 基本マスタ / システム設定 / 管理ツール が並列 | `設定` 1つ。中に コース・料金 / スタッフ / 支払方法 / 営業時間 … |

「マスタ」と「設定」の区別は**実装都合**（マスタテーブルかどうか）であって、
利用者から見ればどちらも「普段は触らない、変えると全体に効くもの」でしかない。

設定は**必ずメニューの末尾**に置く。使用頻度が最も低く、かつ探すときは「一番下」と決まっている方が速い。

## 4. 階層は2段まで

**グループ > 項目 の2段で止める。3段目を作らない。**

3段目が欲しくなったら、それは**画面内のタブ・セクションに降ろすべきもの**（タブは [components.md](./components.md) の Tabs）。
メニューの3段目は、開かないと見えない・現在位置が分からない・モバイルで操作しにくい、と
いいことがない。

```
OK:  設定 > 営業時間
NG:  設定 > 時間設定 > 営業時間
     → 「時間設定」画面を作り、その中のタブで 営業時間 / 早番遅番切替 / 日付切替 を出す
```

## 5. 親項目に固有の画面を持たせない

**子を持つ項目は開閉するだけ。href を持たせない。**

親が href を持ち、かつその href が子のどれかと同じだと、**同じ画面がメニューに2回現れる**。
利用者はどちらを押せばいいか判断できず、片方を押したときだけ選択状態の表示がズレる。

```ts
// NG: 親と子が同じ画面を指す
{ label: "売上", href: "/sales/summary", children: [
    { label: "月報", href: "/sales/summary" },   // ← 親と同じ
] }

// OK: 親は開閉だけ
{ label: "売上", children: [
    { label: "日報", href: "/sales/daily" },
    { label: "月報", href: "/sales/summary" },
] }
```

子を持たない項目は当然 href を持つ。**「子があるなら href なし」が原則。**

## 6. 1グループ 7 項目まで

グループ内の項目が **7 を超えたら、オブジェクトの切り方を疑う**。
たいていは「本来1つのオブジェクトの設定項目」がバラバラに項目化されている。

```
NG: 設定 > 営業時間 / 早番遅番切替時間 / 日付切り替え時間 / ポイント設定 /
          ポイントカレンダー / 入会金 / 計算設定 / 表示項目設定 / 除外年月 / …（12個）

OK: 設定 > 営業時間（中のタブで 営業時間・早番遅番・日付切替）
         > ポイント（中のタブで ポイント設定・カレンダー）
         > 料金計算（中のタブで 入会金・計算設定・除外年月）
         > 表示項目
```

項目を減らすのではなく、**関連するものを1オブジェクトに束ねて画面内のタブにする**（§4 と同じ動き。タブの仕様は [components.md](./components.md) の Tabs）。

## 7. 動詞はメニューに出さない

「新規作成」「申請する」「スキャンする」はメニュー項目ではない。
**オブジェクトの画面を開いて、そこにある主アクション**として置く。

| ❌ メニュー項目 | ✅ 置き場所 |
|---|---|
| 新規受付 | `受付` 画面の主アクション（`Button`、[components.md](./components.md)） |
| QR スキャン | `受付` 画面のアクション、または受付作成フロー内の手段 |

例外は**そのアクション自体が独立した業務**になっている場合（例: 複数オブジェクトを横断して
処理する「振込作業」）。この場合は動詞ではなく**その業務のオブジェクト名**を探して項目名にする。

## 8. 並び順

1. **使用頻度の高い順**。毎日開くものを上に置く
2. 業務の流れがあるならその順（受付 → 顧客 → 売上）
3. **設定は必ず末尾**（§3）
4. グループ名は**名詞**にする（「売上管理」ではなく「売上」。§7 と同じ理由で動詞・サ変名詞を避ける）

アルファベット順・五十音順にしない（利用者は名前ではなく「いつもの位置」で探す）。

## 9. 業務画面（to B）のヘッダー

サイドバーを持つ業務画面の上端に置く帯（ヘッダー）。**左にパンくずと今のページ名（`<h1>`）、右に通知とユーザーメニュー**を置く
（Shopify の管理画面のタイトルバー、shadcn のサイドバー型レイアウトと同じ型）。
第 2 部のトップ階層のヘッダー（§13）・下層ヘッダー（§14）はスマホ中心の画面（to C）のもので、to B では使わない。

### 9-1. 構成

| 項目 | `lg` 以上 | `lg` 未満 |
|------|-----------|-----------|
| 枠 | `sticky top-0 flex h-16 items-center justify-between gap-2 border-b border-border bg-card px-2 md:px-4`。重なりは [layout.md](./layout.md) のナビの層。影は付けない | 同左 |
| 左 | パンくずの親の階層（§9-2）+ 今のページ名の `<h1>`。トップ階層の画面は `<h1>` だけ | 先頭のボタン（トップ階層はハンバーガー、下層は戻る。§9-3）+ 今のページ名の `<h1>` |
| 右 | ヘルプ（§9-6）→ 通知（§9-4）→ ユーザーメニュー（§9-5）。無いものは詰める | 同左 |
| ロゴ | サイドバーの上端 | ドロワー（サイドバーを開いたもの）の上端。帯には出さない |

| 要素 | クラス・規定 |
|------|------------|
| 左の外枠 | `flex min-w-0 items-center gap-1`（右側は `shrink-0`。狭い幅で縮むのは左だけ） |
| 今のページ名 | `<h1>`。`truncate text-base font-semibold text-foreground`。長い名前は省略し、`title` に全文。幅に関係なく同じ要素を 1 つだけ出す |

**ページの `<h1>` はこの帯に置き、本文には大きい見出しを置かない。** 本文の先頭は、補足情報とページの操作だけの行にする
（[components.md](./components.md) の PageHeader）。

- 理由: 帯にパンくずを出したうえで本文にも大きい見出しを置くと、同じ語が上下に 2 回並ぶ（[design.md](./design.md) の「無駄な要素を置かない」）。
  帯は幅に関係なく見えているので、スマホ幅でもページ名がどこかに見えている状態を保てる。
- `<h1>` は `text-base`。パンくずの親（`text-sm`）より 1 段だけ大きくして「今いる場所」を区別しつつ、1 行に並べたときに
  文字の高さが揃う範囲に収める。`text-lg` 以上にすると、`h-16` の帯の中で右のユーザーメニュー（`text-sm`）との差が開き、
  帯だけ見出しが浮いて見える。文字サイズは to C の下層ヘッダーの画面名（§14-1、`text-base`）と揃う。
- ヘッダーに置くのはこの表のものだけ。画面固有の操作（新規作成・編集）は本文の先頭の行に置く。

### 9-2. パンくず（`lg` 以上）

**下層画面の戻る導線は帯のパンくずで担う。本文の先頭に「← 〜に戻る」リンクを置かない。**
戻るリンクとパンくずを両方置くと、同じ行き先が 2 つ並ぶ（[design.md](./design.md) の「無駄な要素を置かない」）。

| 規定 | 理由 |
|------|------|
| 階層は **URL の親子で固定**して組む（例: 会員 › 佐藤 美咲）。メニューのグループ名（開閉するだけの親。§5）は入れない | グループ名は押しても行き先が無い |
| **どこから来たかで変えない。** 第 2 部の `?from=` で戻り先を受け取る仕組み（§14-3）は to B には適用しない | パンくずは「今いる場所」を示すもの。来た経路で親が変わると、同じ画面の位置づけが毎回変わる。元の画面に戻りたいときはブラウザの戻るがある |
| トップ階層の画面（メニューの項目そのもの）では親が無いので、`<h1>` だけになる | 1 項目だけのパンくずは `<h1>` と同じ語の繰り返し |
| 親の階層と `lg` 未満の戻る先は **1 つの定義から引く** | 幅によって戻る先がずれない |
| 読み込み中は、親の階層まで出して `<h1>` の文字だけ後から足す。高さは変えない | 帯を Skeleton にしない（§16） |

| 要素 | クラス・規定 |
|------|------------|
| 外枠 | `<nav aria-label="パンくずリスト" class="hidden min-w-0 lg:block">` の中に `<ol class="flex items-center gap-1 text-sm">`。親の階層だけを入れ、`<h1>` は `<nav>` のすぐ後ろに置く |
| 親の階層 | `<li class="flex shrink-0 items-center gap-1">` にリンクと区切り。リンクは `inline-flex min-h-11 items-center rounded-md whitespace-nowrap text-muted-foreground hover:text-foreground` + [components.md](./components.md) §1-1 のボタン類のリング。hover は文字色だけ変える（[components.md](./components.md) §1-6） |
| 区切り | 各親の後ろに右向きの山括弧 16px（`size-4 shrink-0 text-icon`）、`aria-hidden="true"` |

- 今のページは `<h1>` が示すので、`<nav>` の中に同じ名前を `aria-current="page"` で重ねない。
- ブラウザの履歴（`history.back()`）に頼らず、固定の親に戻す。

### 9-3. `lg` 未満の先頭のボタン

パンくずが入らないので、帯の先頭のボタン 1 つと `<h1>` だけにする。

| 画面 | 先頭のボタン |
|------|------------|
| トップ階層 | ハンバーガー（サイドバーをドロワーで開く）。アイコンだけのボタン（`size-11`、アイコン 24px）、`aria-label="メニューを開く"` |
| 下層 | **戻る**。見た目は to C の下層ヘッダーの戻るボタン（§14-1）と同じ（`size-11`、左向きの矢印 24px）。行き先は §9-2 の直前の親、`aria-label` は「〈親の名前〉に戻る」 |

- 下層の画面ではハンバーガーを出さない。戻るを押せばトップ階層に出てハンバーガーが使える。先頭に 2 つ並べると、
  どちらが戻るか一目で分からず、`<h1>` の幅も削られる。
- 切り替えは `lg`（サイドバーをドロワーにする境界と同じ）。`hidden lg:block` / `lg:hidden` のように完全なクラスで持つ。

### 9-4. 通知

| 要素 | 規定 |
|------|------|
| 押す所 | アイコンだけのボタン（`size-11`）、ベル 24px（`size-6`）。`aria-expanded` |
| 未読 | StatusBadge の dot をアイコンの右上に重ね、`ring-2 ring-card` で縁取る（[components.md](./components.md) §5-3）。dot は `aria-hidden="true"` にし、ボタンの `aria-label` を「通知（未読 3 件）」のようにする |
| 開いた中身 | ポップオーバー（[components.md](./components.md) §16） |

### 9-5. ユーザーメニュー

| 要素 | 規定 |
|------|------|
| 押す所 | **名前 + 小さい下向きの山括弧のテキストボタン**。`inline-flex min-h-11 items-center gap-1 rounded-md px-3 text-sm font-medium text-foreground hover:bg-foreground/5` + [components.md](./components.md) §1-1 のリング。山括弧は 16px（`size-4 text-icon`、`aria-hidden="true"`）。名前は `max-w-40 truncate` |
| 置かないもの | アバター（丸い頭文字）、役職・所属の 2 行目（[design.md](./design.md) の「無駄な要素を置かない」） |
| 押すと | Menu（[components.md](./components.md) §16。ボタンの ARIA もそこが正）。右端を揃えて下に開く。項目は「個人設定」「ログアウト」など |

- ログアウトは破壊的な操作ではないので通常の項目にし、確認ダイアログを出さない。

### 9-6. ヘルプ（AI チャット・マニュアルの入口）

AI チャット（support-chat）やマニュアルの入口は、帯の右の **「?」1 つ**にまとめる。
画面の右下に常駐する丸いボタン（チャットの起動ボタン）は業務画面では出さない。

| 要素 | 規定 |
|------|------|
| 押す所 | アイコンだけのボタン（`size-11`）、丸の中の「?」24px（`size-6`、lucide の `CircleHelp`）。`aria-label="ヘルプ"` |
| 押すと | 入口が 2 つ以上なら Menu（[components.md](./components.md) §16）。項目は「AI チャットに相談」（AI に名前があるなら「〈名前〉に相談」）→「マニュアル」の順。入口が AI チャットだけなら Menu にせず、押したらチャットのパネルを直接開く（[components.md](./components.md) §16-1 の「操作が 1 つならメニューにしない」） |
| チャットのパネル | 「?」の直下（8px 下）に、右端を「?」に揃えて開く。高さは `70vh` と画面に収まる高さの小さい方。幅 480px 以下は全画面。**モーダルにしない**（暗幕なし・外側のクリックで閉じない。回答を見ながら画面を操作するため）。閉じるのはパネルの × と Esc だけで、閉じたら画面に何も残さない |
| フォーカス | 開いたら入力欄。閉じたら「?」に戻す。Menu の項目から開いたときは、Menu が閉じるときに「?」へフォーカスを戻す既定の動きを止める（止めないと入力欄のフォーカスを奪う） |
| 重なり | パネルはウィジェット側が最前面に出す（[layout.md](./layout.md) §4 の表の外の単発の UI）。モーダルを開いたままでもチャットを読めるようにするため |

- 右下の常駐ボタンを出さない理由: 業務画面の右下には保存バー・送信ボタン・ページ送りが来るので、重なって押せなくなる。
  入口がヘッダーにあれば、使わない人の画面には何も増えない（[design.md](./design.md) の「無駄な要素を置かない」）。
  Stripe・Shopify など業務向けの管理画面も、ヘルプと AI アシスタントの入口を上部のバーに置いている。
- 右下の常駐ボタンは、ヘッダーの無い画面（to C の一部・LP）でだけ使ってよい。
- 埋め込み方（右下のボタンを出さないモード・パネルを開く JS API）は support-chat の `widget/README.md` が正。
- 「?」は通知より左に置く。毎回見るもの（通知・自分の名前）を右端に寄せ、たまにしか使わないヘルプを外側にする。

## 10. レビュー用チェックリスト

メニュー・ヘッダーを追加・変更する差分に対して当てる。

- [ ] 追加した項目は**オブジェクト（名詞）**か（動詞・役割・データの性質になっていないか）
- [ ] そのオブジェクトは**既にメニューのどこかに無い**か（2箇所目になっていないか）
- [ ] ロールごとにツリーを分岐させていないか（`visible` で表示制御しているか）
- [ ] スコープで分けたなら、**語幹が一致**し接尾辞が `管理` になっているか（`一覧` を使っていないか）
- [ ] 設定系を新しいトップレベルグループとして足していないか（既存の `設定` に入れたか）
- [ ] **3段目**を作っていないか
- [ ] 子を持つ項目に **href を付けていない**か
- [ ] グループ内が **7 項目**を超えていないか
- [ ] 設定が末尾にあるか
- [ ] to B のページ名の `<h1>` が帯（パンくずの後ろ）に 1 つだけあり、本文に大きい見出しを置いていないか
- [ ] to B の下層画面の戻る導線が帯のパンくずか（本文の先頭に「← 〜に戻る」を置いていないか）。`lg` 未満は戻るのアイコンボタンか
- [ ] パンくずの親と `lg` 未満の戻る先を、URL の親子の 1 つの定義から引いているか（`?from=` で変えていないか）
- [ ] ユーザーメニューが名前 + 下向きの山括弧だけか（アバター・役職の 2 行目を置いていないか）
- [ ] AI チャット・マニュアルの入口が帯の「?」1 つにまとまっているか（右下に常駐の起動ボタンを出していないか）

# 第 2 部 スマホ中心の画面のナビ

## 11. 骨格

**主要な行き先はボトムタブバー、1 段入った画面は「戻る + 画面名」の下層ヘッダー**で組む。
`lg` 以上ではタブバーをやめ、ヘッダーのテキストリンクに切り替える。

| 幅 | ヘッダー（上） | ナビ（下） | 本文の先頭 |
|----|---------------|-----------|-----------|
| `lg` 未満・タブ直下の画面 | トップ階層のヘッダー（ロゴ）（§13） | ボトムタブバー（§12） | 見出しは `sr-only` |
| `lg` 未満・1 段入った画面（名前を持つ画面） | 下層ヘッダー（戻る + 画面名）（§14） | ボトムタブバー | 戻るリンクは出さない。見出しは `sr-only`（ヘッダーの画面名と同じ語のため） |
| `lg` 未満・1 段入った画面（一覧から入った個別のレコードの詳細） | 下層ヘッダー（戻る + 属するタブの名前）（§14） | ボトムタブバー | 戻るリンクは出さない。**見出し（レコードのタイトル）は見せる** |
| `lg` 以上 | トップ階層のヘッダー + タブのテキストリンク | なし | 1 段入った画面は戻るリンク + 見える見出し |

- 切り替えは `lg`。ナビの出し方は画面の骨格の切り替えにあたる（[layout.md](./layout.md)）。
- **タブの項目定義は 1 つ。** 1 つのナビ要素をブレークポイントで描き分け、タブバー用とヘッダー用に
  項目を 2 回書かない（片方だけ項目が増える・消えるズレが起きる。§2 と同じ理由）。
- タブの項目の立て方は第 1 部に従う（オブジェクトで立てる、動詞を出さない、権限は `visible` で切る）。

## 12. ボトムタブバー

### 12-1. 構成

| 項目 | 規定 |
|------|------|
| 出す幅 | `lg` 未満だけ |
| 項目数 | **3〜5 個**。6 個目が欲しくなったら、行き先をハブ画面（マイページ等）の中に降ろす |
| 各タブ | **アイコン + ラベル**の縦積み（`flex-col items-center justify-center gap-1`）。アイコンだけのタブにしない |
| 幅 | 全タブ等幅（`grid grid-flow-col auto-cols-fr`）。各タブは `w-full` |
| アイコン | 20px（`size-5`）。線のアイコン、選択中は同じ形の塗り版（[components.md](./components.md) のアイコン） |
| ラベル | `text-xs font-medium leading-tight whitespace-nowrap`。1 語の名詞（第 1 部 §1） |
| 押せる領域 | タブ 1 つの高さ全体（`min-h-(--tabbar-height)`）× 幅全体 |
| 項目の出し分け | 権限で出さないタブは `visible` で外す。ツリーを権限ごとに分けない（§2） |

### 12-2. 状態

| 状態 | ラベル | アイコン |
|------|--------|---------|
| 選択中 | `font-semibold text-foreground` | 線 `text-icon-strong` + 塗り `fill-icon-fill` |
| 非選択 | `text-muted-foreground` | 線 `text-icon`、塗りなし |
| hover | 変えない | 変えない |
| focus-visible | [components.md](./components.md) のボタン類のリング | — |

- **選択中は太さ（`font-medium` → `font-semibold`）と色（`text-muted-foreground` → `text-foreground`）の両方で示す**（色だけで状態を伝えない）。
  タブバーと `lg` 以上のヘッダーのテキストリンク（§12-5）の両方に当てる。
- **ナビにはブランド色（`text-primary`）を使わない。** ブランド色が黒系でない場合、選択中のラベルだけ色が浮き、アイコンの色ともずれるため。

- 選択中のリンクに `aria-current="page"` を付け、色の切り替えもこの属性で行う（`group-aria-[current=page]:` 等）。
  状態を JS の条件分岐とクラスの両方に持つと、片方だけ更新されてズレる。
- **選択の判定は前方一致**にする。一覧から入った詳細画面でも、親のタブを選択中のままにする
  （どこにいるかがタブバーから分かる）。
- タッチ端末では hover で色を変えない。押した後も hover の色が残り、選択中と見分けにくくなる。
- 未読・未対応があるタブは、件数ではなく **dot（8px）をアイコンの右上に重ねる**
  （[components.md](./components.md) の StatusBadge の dot、`ring-2 ring-card` で縁取り）。
  dot は `aria-hidden="true"` にし、タブのリンクの `aria-label` に「通知（未読あり）」のように状態を足す。

### 12-3. 寸法・位置・safe-area

| 項目 | 規定 |
|------|------|
| 高さ | **56px**。CSS 変数 `--tabbar-height` で 1 箇所に持つ（クラスでは v4 `min-h-(--tabbar-height)`、v3 `min-h-[var(--tabbar-height)]`） |
| 位置 | `fixed inset-x-0 bottom-0`。重なりは [layout.md](./layout.md) のナビの層 |
| 面 | `bg-card border-t border-border`。影は付けない（[components.md](./components.md) の影） |
| 下端の余白 | `pb-[calc(env(safe-area-inset-bottom)+0.75rem)]`（safe-area に 12px を足す） |

**`--tabbar-height` と `--tabbar-offset` はプロダクト側の CSS で定義する。** core のトークン（`tokens.css` / `v4.css`）には無い。
グローバルの CSS に次の 2 つを 1 回書く。

```css
:root {
  --tabbar-height: 56px;
  /* タブバーが画面下から占める高さ（高さ + 下端の余白 12px + safe-area） */
  --tabbar-offset: calc(var(--tabbar-height) + 0.75rem + env(safe-area-inset-bottom));
}
```

`--tabbar-offset` の `0.75rem` は上の表の下端の余白（safe-area に足す 12px）と同じ値。
タブバーの高さは `--tabbar-height`、本文の下余白（§12-4）・トースト（[components.md](./components.md) の Toast）の位置は
`--tabbar-offset` から引く。

**下端に safe-area + 12px を足す理由**

- `env(safe-area-inset-bottom)` は iPhone のホームインジケーターの領域。これが無いとタブが
  ホームインジケーターに重なり、タブを押したつもりでアプリ切り替えが起きる。
- さらに **12px を足す**のは、safe-area が 0 の環境（Android・PC・LINE などのアプリ内ブラウザ）でも、
  画面下端に重なるブラウザ自身のツールバーとタブを離すため。隣接していると誤タップが起きる。
- `env(safe-area-inset-*)` は viewport に `viewport-fit=cover` を指定したときだけ値が入る。
  指定しない場合は 0 になり、足すのは 12px だけになる。

### 12-4. 本文がタブバーに隠れないようにする

- タブバーは `fixed` なので、本文の末尾（フッター・最後のボタン）がタブバーの下に潜る。
- **レイアウトの外枠に、タブバーと同じ高さの下余白を `lg` 未満だけ付ける**: `max-lg:pb-[var(--tabbar-offset)]`
- 値は §12-3 の `--tabbar-offset` から引き、計算式を書き写さない。タブバー・下余白・トーストの位置が
  同じ変数を見るので、タブバーの寸法を変えても食い違わない。
- 下余白は各ページではなく、レイアウト側で 1 回だけ付ける（[layout.md](./layout.md)）。

### 12-5. `lg` 以上（ヘッダーのテキストリンク）

| 項目 | 規定 |
|------|------|
| 位置 | トップ階層のヘッダーの右側に横並び（`flex items-center gap-1`）。アイコンは出さない |
| 各リンク | `inline-flex min-h-11 items-center rounded-md px-3 text-sm font-medium` |
| 選択中 | `font-semibold text-foreground` |
| 非選択 | `text-muted-foreground hover:text-foreground` |

選択中の示し方とブランド色を使わない理由は §12-2。

## 13. トップ階層のヘッダー

タブ直下の画面と、`lg` 以上のすべての画面で使う。

| 項目 | 規定 |
|------|------|
| 高さ | `h-16`（64px） |
| 面 | `bg-card border-b border-border`。影は付けない |
| 位置 | `sticky top-0`。重なりは [layout.md](./layout.md) のナビの層 |
| 内側 | `mx-auto flex items-center justify-between px-4`。最大幅はページ本文と揃える（[layout.md](./layout.md)） |
| 左 | ロゴ（高さ `h-7`、28px）。ログイン時はホームへ、未ログイン時は公開ページの入口へリンクする |
| 右（ログイン時） | `lg` 以上はタブのテキストリンク（§12-5）。どの画面からも 1 タップで開きたいもの（会員証など）に限り、アイコンボタンを 1 つ置ける |
| 右（未ログイン時） | ログインボタン（Button `primary`、`md`）。**今いる画面のパスを引き継ぐ**（ログイン後に元の画面へ戻す） |

- ロゴの `<img>` には `width` / `height` 属性（画像の固有サイズ）を付ける。読み込み完了前から
  比率で幅が確保され、ロゴの表示でヘッダーの中身がずれない。
- タブ直下の画面では、ページの `<h1>` を `sr-only` にする（[components.md](./components.md) の PageHeader）。
  いまどのタブにいるかはタブバーが示している。
- **フッターは未ログインの画面だけ**に出す。ログイン後はタブバーが常にあるので、
  規約・プライバシーポリシー等への導線はハブとなるタブ（マイページ等）の中に集約する。
- ヘッダーに置くのはロゴ・タブ・アイコンボタン 1 つ・ログインだけ。それ以外の導線はタブの中に置く。

## 14. 下層ヘッダー（戻る + 画面名）

一覧から 1 段入った画面（詳細、マイページ配下の各セクション等）で、`lg` 未満のときにトップ階層のヘッダーと差し替える。

### 14-1. 構成

| 項目 | 規定 |
|------|------|
| 枠 | トップ階層のヘッダーと同じ（`h-16 bg-card border-b border-border sticky top-0`、ナビの層）。`relative` は足さない（`sticky` も中央の画面名の `absolute` の基準になる。position を 2 クラスで指定すると、勝敗が CSS の生成順で決まる） |
| 左 | 戻るボタン。アイコンだけのボタン（`size-11`）に左向きの矢印 24px（`size-6`）。`aria-label` は「〈戻り先〉に戻る」 |
| 中央 | 画面名。`text-base font-bold text-foreground` で 1 行。**左右のボタンの有無に関係なく行の中央に置く**（`absolute inset-x-0 text-center pointer-events-none`） |
| 右 | 既定は何も置かない（§14-4） |
| ロゴ | 出さない |

- 画面名は `<p>` にし、見出しにしない。ページの `<h1>` は本文側に置く。ヘッダーにも `<h1>` を置くと、1 画面に `<h1>` が 2 つになる。
- 本文の `<h1>` を `lg` 未満で隠すかは §14-2。
- 本文に戻るリンクを置かず、ヘッダーに戻るを出す理由: 本文側に置くと 1 行ぶん内容が下がるうえ、
  親指の届きにくい左上付近に小さなリンクが来る。

### 14-2. 画面名の付け方

| 画面の種類 | 画面名 | 本文の `<h1>`（`lg` 未満） | 例 |
|-----------|--------|---------------------------|-----|
| 一覧から入った個別のレコードの詳細 | **属するタブの名前** | **レコードのタイトルを見せる** | 通知一覧 → 通知詳細なら、画面名「通知」、`<h1>` は通知の件名 |
| それ自体が名前を持つ画面（マイページ配下の各セクション・設定の下層） | **その画面の名前** | 画面名と同じ語を `sr-only` | 「基本情報」「連絡先」 |

この表の `<h1>` の扱いは**下層ヘッダーを使う画面（to C）だけ**のもの。to B の `<h1>` は上の帯に置く（§9-1）。

個別のレコードのタイトル（記事の見出し等）はヘッダーに入れず、本文の `<h1>` に置く（長いタイトルを 1 行の中央に入れると切れる）。
ヘッダーにはタブの名前しか出ないので、この `<h1>` を隠すとスマホでタイトルがどこにも見えなくなる。

### 14-3. 戻る先の決め方

| 規定 | 理由 |
|------|------|
| **固定の親**（一覧、またはハブ画面）に戻す。ブラウザの履歴（`history.back()`）に頼らない | ログイン・登録など外部の画面を挟んで戻ってくると、履歴の 1 つ前が外部の画面になる。直リンクで開いた場合は履歴自体が無い |
| 入口が複数ある詳細画面は、**元の画面を URL パラメータで受け取る**（`?from=/path` 等） | 既定の一覧に戻されると、元の画面（ホーム、別の詳細）に戻れなくなる |
| 受け付ける `from` は**許可リストにある形だけ**。それ以外（外部 URL・未知のパス）は既定の親に倒す | 任意の URL へ飛ばせるとオープンリダイレクトになる |
| 戻り先と読み上げ名（「〈戻り先〉に戻る」）は 1 つの定義から引く | 行き先と文言がずれない |

戻り先の定義は、画面本体と読み込み中の表示の両方から同じものを参照する（§16）。

### 14-4. 右端のアクション

- **既定は置かない。** 画面名が中央に固定されているので、置いても置かなくても位置はずれない。
- 置けるのは、**その画面でトップ階層のヘッダーの右端と同じ操作が必要なとき**の 1 つだけ
  （例: 当日に会員証を出す画面での会員証のボタン）。アイコンだけのボタン（`size-11`、アイコン 24px）、`aria-label` 必須。
- 編集・削除などその画面固有の操作はヘッダーに置かず、本文の中に置く。

### 14-5. `lg` 以上

- ヘッダーはトップ階層のもの（ロゴ + タブのテキストリンク）に戻す。
- 本文の先頭に**戻るリンク**と**見える `<h1>`** を出す。

| 要素 | 規定 |
|------|------|
| 戻るリンク | `inline-flex min-h-11 items-center gap-1 text-sm text-muted-foreground hover:text-foreground`、左向きの矢印 16px。文言は「〈戻り先〉に戻る」 |
| 見出し | `<h1>`。サイズは [typography.md](./typography.md) のページ見出し |

- **ヘッダーの戻ると本文の戻るリンクの切り替え境界を同じ `lg` にする。** ずれると、
  戻るが 2 つ出る幅・どちらも出ない幅ができる。表示の切り替えは完全なクラス（`hidden lg:inline-flex` 等）で持ち、
  `inline-flex` と `hidden` を 1 つの要素に並べて勝敗を CSS の順序に任せない。

## 15. モーダルとして開く画面

| 形 | 使う場面 | ヘッダー |
|----|---------|---------|
| 通常の遷移（下層ページ） | 一覧 → 詳細など、**URL を持ち、共有・再訪・ブラウザの戻る**で行き来する画面 | 下層ヘッダー（§14） |
| 全画面の編集モーダル | **今の画面の内容の一部を編集し、保存して元の画面に戻る**もの（プロフィールの各セクションの編集など） | 下層ヘッダーと同じ形で、左が × （`aria-label="閉じる"`）、中央のタイトルは `<h2>` |
| モーダル風のページ | URL は必要だが、**開いて読んだら閉じる**性質のページ（利用規約・プライバシーポリシー）。他の画面から新しいタブで開かれることもある | 下層ヘッダーと同じ形で、左が ×、中央のタイトルは `<h1>` |
| 確認ダイアログ | 実行の確認だけ（入力しない） | なし（[components.md](./components.md)） |

- 編集モーダルは `md` 未満で全画面、`md` 以上で中央のダイアログにする。寸法・フッターは [components.md](./components.md) の全画面の編集モーダル。
- 全画面で出すもの（編集モーダル・モーダル風のページ）は、ヘッダーの**上に safe-area の余白**を足す
  （`box-content pt-[env(safe-area-inset-top)]`）。ノッチにタイトルや × が重ならないようにする。
- モーダル風のページの × は、**同じタブに履歴があれば戻り、無ければ既定の画面へ遷移**する。
  新しいタブで開いた場合は履歴が無く、戻る先が無いため。
- 入力を伴う編集をページ遷移にしない。保存後に元の画面のスクロール位置や開閉状態が失われる。
  逆に、詳細画面をモーダルにしない。URL が無いと共有・再訪・ブラウザの戻るが効かない。

## 16. 読み込み中のヘッダー

**読み込み中もヘッダーの形を変えない。** ヘッダーが読み込み完了の瞬間に差し替わると、
押そうとした戻るボタンの位置が動く。

- 画面本体と読み込み中の表示（Next.js なら `page` と `loading`）に、**同じヘッダー指定**（画面名・戻り先・右端の有無）と
  **同じ地色**を渡す。指定は 1 箇所に定数で置き、両方から参照する。
- **ヘッダーは Skeleton にしない。** Skeleton にするのは本文だけ（[components.md](./components.md) の Skeleton）。
- 本文の Skeleton は、その幅でヘッダーが担っているもの（`lg` 未満の戻る・画面名）の枠を確保しない。
  個別のレコードの詳細の `<h1>`（タイトル）は `lg` 未満でも見えるので、その枠は確保する。
  `lg` 以上で本文に出す戻るリンクの枠は、`lg` 以上だけ確保する。
- ログイン状態の判定を待つ画面では、判定が終わるまで**同じ高さの仮のヘッダー**（未ログイン状態のヘッダー）を出す。
  ヘッダーの高さが後から変わると、本文全体が下にずれる。
- ロゴの `width` / `height` 属性（§13）も同じ目的。読み込み中にヘッダーの中身をずらさない。

## 17. レビュー用チェックリスト（スマホ中心の画面のナビ）

- [ ] タブが 3〜5 個で、各タブがアイコン + ラベルか
- [ ] タブの項目定義が 1 つで、タブバーとヘッダーのリンクを同じ定義から描いているか
