# マニュアル

業務アプリ（to B）の**マニュアル**（画面の中で読める、利用者向けの使い方の手引き）の置き場・構成・ページの書き方・画像・レイアウト・検証。
**マニュアルは 1 画面 1 ページで書き、アプリに同梱する。**

入口（上の帯の「?」）は [navigation.md](./navigation.md) §9-6、文体は [writing.md](./writing.md)、画像の代替テキストは [a11y.md](./a11y.md) §10、
読み物の文字・行長は [typography.md](./typography.md) §2-1、最大幅は [layout.md](./layout.md) §2 を参照。

## 0. マニュアルとは何か

| もの | 役割 | 読む・使う人 |
|------|------|-------------|
| **マニュアル**（この文書） | 画面ごとの使い方を、人が自分で読んで探す | 利用者 |
| AI チャット（support-chat） | 利用者の質問に答える | 利用者 |
| 各アプリの `docs/screens.md`・`docs/faq.md` | 画面の仕様とよくある質問の**正** | 開発者・AI チャット・マニュアルを書く人 |

- マニュアルと AI チャットは別のもの。**どちらも `docs/screens.md`・`docs/faq.md` に合わせて書き、仕様をマニュアル側で決めない。**
  マニュアルに書いてあることと画面・仕様が食い違ったら、仕様（`docs/screens.md`）を正として直す。
- 推測で書かない。仕様に無い動きは、先に `docs/screens.md` を確かめてから書く。

## 1. 置き場

| 項目 | 規定 |
|------|------|
| リポジトリ | **各アプリのリポジトリに置く**（全社で 1 か所にまとめない） |
| 本文 | markdown。**アプリに同梱する**（ビルド時に取り込み、実行時にファイルを読まない） |
| 画像 | アプリの静的ファイル（例: `public/images/manual/`） |
| 直すタイミング | **画面を変える PR で、同じ PR の中でマニュアルも直す**（文言・手順・画像） |

- 各アプリに置く理由: 画面を変える人が同じ PR でマニュアルを直せる。別の場所に置くと直し忘れ、画面とマニュアルが食い違ったまま残る。
- 同梱する理由: サーバーレスの実行環境では、実行時に読むファイル（`docs/*.md` 等）が関数のバンドルに含まれず、本番だけ読めなくなる。
  本文はモジュールとして取り込み、ビルドの成果物に含める。
- 本文はサーバー側で HTML にしてから返す。markdown の描画部品をブラウザに送らない（初期表示の往復と配る JS を減らす）。

## 2. 入口と URL

| 項目 | 規定 |
|------|------|
| 入口 | 上の帯の「?」の「マニュアル」（[navigation.md](./navigation.md) §9-6）。**どの画面からも同じ位置で開ける** |
| サイドメニュー | 置くかは任意。置くならメニューの末尾（「設定」のグループの中）に 1 項目だけ。新しいトップレベルのグループを作らない（[navigation.md](./navigation.md) §3） |
| 名前 | 「マニュアル」。帯の「?」の項目名と同じ語にし、「ヘルプ」「使い方」「ユーザーガイド」と混ぜない（[writing.md](./writing.md) §9） |
| URL | トップは `/manual`、各ページは `/manual/<slug>`。アプリの都合で接頭辞を付けてよい（`/admin/manual/<slug>` 等） |
| slug | 英小文字・数字・ハイフンだけ（`attendance-detail`）。画面の URL の末尾と揃えると探しやすい |
| 開き方 | 同じタブで開く。新しいタブで開くなら [components.md](./components.md) §1-4 の外部リンクの規定を当てる |

## 3. 構成

**トップ 1 ページと、1 画面 1 ページ**で組む。長い 1 ページにまとめない。

| ページ | 中身 |
|--------|------|
| トップ（`/manual`） | 上から ①はじめての方への案内 → ②やりたいこと・仕事の流れから探す → ③画面ごとの使い方（カード） |
| 画面ごとのページ（`/manual/<slug>`） | 1 画面の使い方（§4） |
| 手順のページ（任意） | 画面をまたぐ仕事の手順（「月末の締め」など）。画面ごとのページと同じ形で書き、各段から画面ごとのページへリンクする |
| はじめに（任意） | アプリでできること・画面の見方・まず覚える画面。トップの①の行き先。並びの先頭に置く |

**1 ページにまとめない理由**

- 20 を超える節が 1 ページに並ぶと、長くて読む気がなくなる（利用者の声）。
- 1 ページの中の目次から見出しへ飛ぶ作りでは、飛んだあとに上の画像が読み込まれて高さが増え、見出しが画面の外へ押し出される。
  ページを分ければ、目次の行き先はページの先頭になり、この問題が起きない。
- 画面ごとに分けておくと、画面を変える PR で直す範囲が 1 ページに収まる（§1）。

### 3-1. トップ

| 区画 | 規定 |
|------|------|
| ① はじめての方への案内 | 冒頭に 1 つ。見出し（「はじめての方は、まずここから」等）+ 1 文 + 「はじめに」ページへのボタン 1 つ。押せる所はボタン 1 つに絞る |
| ② やりたいこと・仕事の流れ | 行き先のページをカードで並べる。ふだんの仕事の順に並べるとき（「招待 → 取り込み → 承認」）は `<ol>`（順番に意味があるため）で、各カードは短い見出しだけ（「勤怠を承認する」）。順番の無い「やりたいこと」の一覧（「新しく入る人の準備」「退職の処理」）は `<ul>` にし、1 行の説明を添えてよい |
| ③ 画面ごとの使い方 | グループ（画面群。サイドメニューのグループと揃える）ごとに `<h3>` と、ページのカード（画面名 + 1 行の説明）を並べる。①と同じページ（「はじめに」）はここに出さない |

- トップの `<h1>` は「マニュアル」。本文に長い説明文を置かない（「使いたい画面を選んでください。」の 1 行で足りる）。
- 一覧の並び（グループとページの順）は **1 つの定義**から引き、トップのカード・目次（§6）・前後のページ（§6）で使い回す。
  並びを場所ごとに書くと、片方だけページが増える・消えるずれが起きる（[navigation.md](./navigation.md) §2 と同じ理由）。
- カード全体をリンクにする（[color.md](./color.md) §4「リンクの状態」のカード全体がリンク。下線は不要）。面は Card と同じ（[components.md](./components.md) §6）。

## 4. ページの形

**1 ページ = 1 画面。** 上から次の順に書く。

| 順 | 区画 | 見出し | 中身 |
|----|------|--------|------|
| 0 | 要る権限（ある画面だけ） | なし | その画面を使うのに要る権限を 1 文で（§7） |
| 1 | 画像 | なし | 画面全体の画像 1 枚以上 + キャプション（§5） |
| 2 | できること | `## できること` | その画面でできることの箇条書き。ボタン名・欄名・列名を画面の文言どおりに書く |
| 3 | 手順 | `## 手順` | 番号付きのリスト。1 段に 1 操作（「〜を押す。」） |
| 4 | よくある質問（あれば） | `## よくある質問` | 質問を太字で書き、続けて答え（箇条書きで `- **質問**: 答え` と書いてよい）。`docs/faq.md` に合わせる |

### 4-1. 見出し

| 項目 | 規定 |
|------|------|
| `<h1>` | **画面名そのもの**（サイドメニュー・帯の `<h1>` と同じ語）。帯に置く（[navigation.md](./navigation.md) §9-1）。本文の markdown には `# ` を書かない |
| `<h2>` | 「できること」「手順」「よくある質問」の 3 つに固定する。ページ間で同じ語にし、どのページでも同じ場所で探せるようにする |
| `<h3>` | 手順が 2 つ以上あるときだけ、`## 手順` の下で分ける。見出しはやりたいこと（「まとめて差し戻す」） |
| `<title>` | 「〈画面名〉 \| マニュアル」にサービス名を続ける（[a11y.md](./a11y.md) §3） |
| パンくず | URL の親子どおり（「マニュアル › 〈画面名〉」。[navigation.md](./navigation.md) §9-2） |
| 1 行の説明 | 画面の要約を 1 行（「現場・日ごとの申請状況を見る」）。トップのカードと本文の先頭の補足の行（[components.md](./components.md) §11-1）に出す |

- `<h3>` の見出しを「〜する」で書くのは、[writing.md](./writing.md) §1（ラベルは名詞句）の例外。マニュアルの利用者は**やりたいこと**で探すため。
- 見出しのレベルを飛ばさない（`<h1>` → `<h2>` → `<h3>`。[a11y.md](./a11y.md) §4）。

### 4-2. 文の書き方

| 項目 | 規定 |
|------|------|
| ボタン名 | **画面の文言どおり**に太字で、角括弧で囲む（`**[差し戻す]**`）。前後に半角の空白か句読点を置く（`で **[保存]** を押す`。日本語の文字に直に続けると markdown の強調にならず、`**` がそのまま出る） |
| 欄・列・メニュー・タブの名前 | 画面の文言どおりに太字で、鉤括弧で囲む（`「**勤怠一覧**」`） |
| 手順の 1 段 | 1 操作で、「〜を押す。」「〜を選ぶ。」で言い切る。押した結果や補足は同じ段に敬体で続けてよい（「〜を押す（ポータルから届いた勤怠が絞り込まれます）。」） |
| 説明・できること・答え | 敬体（[writing.md](./writing.md) §8-1）。句点は「文には打つ、句には打たない」（§8-2） |
| 別のページへのリンク | 行き先の画面名をリンク文字にする（`[勤怠内訳](/manual/attendance-detail)`）。「こちら」と書かない |
| 1 ページの長さ | 本文 **2,000 字まで**を目安にする。超えるときは手順を手順のページ（§3）に分けるか、画面の作りを疑う（[writing.md](./writing.md) §2-2） |

- 名前を画面の文言どおりに書く理由: 利用者はブラウザのページ内検索（Ctrl+F / ⌘+F）で、画面で見た語をそのまま探す。言い換えると見つからない。
  画面の文言を変えたら、マニュアルの同じ語も同じ PR で直す（§1）。
- 太字にする理由: 読み流したときに、押す所・見る所だけが目に入る。
- 手順の段を「〜を押す。」で言い切るのは、[writing.md](./writing.md) §8-1（敬体）の例外。段の末尾の動詞だけで操作が分かり、番号付きの短い段が並ぶ手順では敬体の語尾が読む量を増やすため。
  手順以外（説明・できること・答え）は敬体で書く。

## 5. 画像

| 項目 | 規定 |
|------|------|
| 撮るもの | **合成データ**を入れた画面（開発用の合成データ・テスト用のアカウント）。**個人情報・実データ（顧客名・氏名・連絡先・金額）を写さない** |
| 範囲 | 画面全体、または説明する区画。PC の画面は同じウィンドウ幅で撮り、ページ間で縮尺を揃える |
| `alt` | **画像が伝えている内容**（どこに何が並んでいるか、印で示している所）。「画像」「スクリーンショット」と書かない（[a11y.md](./a11y.md) §10） |
| キャプション | 画像の直後に 1 行。その画像で何を見ればよいかを書く。`text-sm leading-relaxed text-muted-foreground` で画像に寄せる |
| 注目させる所 | 画像の中で枠で囲む。**囲んだものはキャプションに名前で書く**（「（赤枠=確認完了にする）」）。色だけで伝えない（[a11y.md](./a11y.md) §9）。囲みの色はアプリの中で 1 色に揃える |
| 寸法 | `<img>` に実寸の `width` / `height` を付け、`h-auto w-full` で列の幅に合わせて縮める |
| 読み込み | 遅延読み込み（`loading="lazy"`）にしない |
| 見た目 | `rounded-lg border border-border`。スマホの画面の画像は列の幅いっぱいにせず、`max-w-sm` に抑える |
| 撮り直し | **画面を変えたら、同じ PR で撮り直す**（§1） |

- `width` / `height` を付ける理由: 読み込む前から縦横比どおりの高さを取り、読み込み後に本文がずれない（[navigation.md](./navigation.md) §13 のロゴと同じ）。
- 遅延読み込みにしない理由: 1 ページの画像は数枚なので効果が小さい。目次やリンクで飛んだあとに上の画像が読み込まれると、見出しが押し出される（§3）。
- 合成データで撮る理由: 画像は文字と違って検索で見つけにくく、個人情報が写っていても気づかれないまま配られる。
- **画像なし（文だけ）で始めてよい。** 画像を足すのは、画面のどこを押すかが文だけでは分かりにくい所から。

## 6. レイアウト

| 項目 | `lg` 以上 | `lg` 未満 |
|------|-----------|-----------|
| 全体 | 読み物なので最大幅を付けて中央寄せ（`mx-auto max-w-6xl`。[layout.md](./layout.md) §2） | 同左 |
| 目次 | 左の列（`w-60`）。`sticky` で上の帯の下に貼り付け、画面より長いときは目次の中でスクロールする | 本文の上に「目次」として畳む（`<details>`）。項目を押したら閉じる |
| 本文 | 右の列。列は `max-w-4xl`、文章のブロック（段落・リスト・引用）は `max-w-prose`（[typography.md](./typography.md) §2-1）。PC の画面の画像は列の幅いっぱい | 同左 |
| 前後のページ | 本文の末尾 | 同左（縦に積む） |

### 6-1. 目次

| 項目 | 規定 |
|------|------|
| 段 | 先頭に「トップ」、その下に**グループ → ページの 2 段**（[navigation.md](./navigation.md) §4 と同じく 3 段目を作らない） |
| グループ名 | リンクにしない（`text-sm font-semibold leading-tight text-foreground`） |
| ページ | 1 ページへのリンク。`text-sm leading-tight text-muted-foreground hover:text-foreground`、左に `border-l-2 border-border` |
| 現在地 | `aria-current="page"` を付け、**太さと色の両方**で示す（`font-semibold text-foreground`、左の線を `border-foreground`）。[navigation.md](./navigation.md) §12-2 と同じ |
| 読み上げ | `<nav aria-label="マニュアルの目次">`（サイドメニュー・パンくずの `<nav>` と区別する。[a11y.md](./a11y.md) §3） |

- 目次を貼り付けるときは、任意の値のクラス（`max-h-[calc(...)]`）を書かずに組む。ページ全体がスクロールする作りなら、帯の高さの分だけ下げて（`top-16`）高さを画面の高さまでにし（`max-h-dvh`・`overflow-y-auto`）、帯の分だけ下に余白を足して末尾の項目まで届くようにする。
- 目次とトップのカードのリンクは先読みしない（1 画面に 20 件を超えるリンクが並び、開くたびに全ページを読みに行くため）。
- 目次の下に、ページ内検索の案内（「Ctrl+F（Mac は ⌘+F）で、画面名やボタン名をページの中から探せます。」）を置いてよい。
- AI チャットを入れているアプリは、目次の下に AI チャットを開くボタンを置いてよい。開くパネルは帯の「?」から開くものと同じ（[navigation.md](./navigation.md) §9-6）。

### 6-2. 前後のページ

- 本文の末尾に、**前のページ・次のページ**へのリンクを置く（`<nav aria-label="前後のページ">`）。各リンクは「前のページ」「次のページ」の小さい文字 + 行き先の画面名。
- 並びはグループをまたいだ全体の順（§3-1 の 1 つの定義）。先頭のページの「前」はトップ、末尾のページは「次」を出さない。
- 理由: はじめての人が「はじめに」から順に読み進められる。目次に戻らずに次の画面へ移れる。

### 6-3. 色・余白・地色・読み込み中

- 色・余白は既存のトークンと段（[color.md](./color.md)・[spacing.md](./spacing.md)）。マニュアル専用の色を作らない。
- 地色はアプリの他の画面と同じ（[layout.md](./layout.md) §3。マニュアルだけ変えない）。
- 本文のブロックの間は `space-y-6`、本文の文字は `text-base leading-relaxed`（[typography.md](./typography.md) §2-1）。本文中のリンクは常時下線（[color.md](./color.md) §4）。
- 読み込み中の表示（Skeleton）を出すなら、目次と本文の 2 列の骨格にする。トップと各ページで同じ骨格を使う（[components.md](./components.md) §8-3）。本文を同梱していてデータの取得を待たないページでは、出さなくてよい。
- 3 つの `<h2>`・目次のグループ・トップのカードにアイコンを添えてよい（文章のかたまりに見えて読む気が起きないのを防ぐため）。添えるなら、同じ見出し・同じグループには全ページで同じアイコンを使い、アイコンだけで意味を伝えない（必ず文字の名前と並べ、`aria-hidden` にする）。

### 6-4. 印刷（任意）

印刷に対応するなら、帯・サイドメニュー・目次・前後のページを `print:hidden` で消し、本文だけを 1 列で出す。画像は `break-inside-avoid` でページの境目で切らない。

## 7. 権限

| 規定 | 理由 |
|------|------|
| **マニュアルのページは権限で隠さない**。トップのカード・目次にも全ページを出す | 権限の無い人も「その画面で何ができるか」「誰に権限を頼めばよいか」を知るため。頼む人と頼まれる人が同じページを見て話せる |
| 読めても操作はできない（画面側の権限はそのまま効く） | マニュアルは読み物で、操作の入口ではない |
| その画面に要る権限は、**ページの冒頭**（画像の前）に 1 文で書く（例「この画面は〈権限名〉の権限がある人だけが使えます。」。役割で決まるなら「この画面を使えるのは、〈役割〉です。」） | 手順を読み進めてから、自分には使えないと分かるのを防ぐ |

- 権限名は画面・権限の設定画面の文言どおりに書く（§4-2）。
- 手順の途中の 1 つのボタンだけに権限が要るときは、その段に書く（「〜を押す（〈権限名〉の権限が要ります）。」）。

## 8. 検証（テスト）

本文とページの並びは、アプリのテストで次を確かめる。**画面で開いて初めて気づく壊れ方を、PR の段階で止める。**

| 確かめること | 防ぐもの |
|-------------|---------|
| slug が重複しない | 同じ URL に 2 ページ |
| slug が英小文字・数字・ハイフンだけ（`^[a-z0-9]+(?:-[a-z0-9]+)*$`） | 大文字・空白・日本語の URL |
| グループ名が重複せず、どのグループもページを持つ | 中身の無い目次のグループ |
| 各ページの画面名・1 行の説明・本文が空でない。本文が `# ` で始まらない | `<h1>` が 2 つになる（§4-1） |
| 本文のページ間リンク（`/manual/<slug>`）の行き先のページがある。トップの「仕事の流れ」の行き先も同じ | ページの改名・削除で切れたリンク |
| 本文の画像が静的ファイルに実在する | パスの書き間違いで画像が出ない |
| 本文の画像の寸法（`width` / `height`）が定義されている | 読み込み後に本文がずれる（§5） |
| 画像の `alt` が空でなく、直後にキャプションがある | 読み上げで中身が分からない画像 |

- 寸法は画像ファイルを測って表（画像のパス → 幅・高さ）に持つか、ビルド時に画像を読み込んで取る。どちらでも、テストで「本文の画像がすべて寸法を持つ」ことを確かめる。
- 画像を足したら、ファイル・寸法・`alt`・キャプションを同じ PR で足す。

## 9. レビュー用チェックリスト

マニュアルを追加・変更する差分と、**画面を変える差分**に当てる。

### 置き場・入口

- [ ] 画面（文言・手順・見た目）を変えた PR で、その画面のマニュアルのページも直したか（画像の撮り直しを含む）
- [ ] 書いた内容が `docs/screens.md`・`docs/faq.md` と食い違っていないか（推測で書いていないか）
- [ ] 本文がアプリに同梱されているか（実行時にファイルを読んでいないか）
- [ ] 入口が帯の「?」の「マニュアル」か。名前を「ヘルプ」「使い方」などと混ぜていないか

### 構成・ページの形

- [ ] 1 画面 1 ページか（複数の画面を 1 ページに詰めていないか）
- [ ] ページの並びを 1 つの定義から引き、トップ・目次・前後のページで使い回しているか
- [ ] 画像 → できること → 手順 → よくある質問の順で、`<h2>` が決まった 3 つの語か
- [ ] `<h1>` が画面名そのもので、本文に `# ` を書いていないか
- [ ] ボタン名・欄名が画面の文言どおりに太字になっているか（描画した本文に `**` が残っていないか。テストで確かめる）
- [ ] 手順が番号付きで、1 段に 1 操作か
- [ ] 本文が 2,000 字を大きく超えていないか

### 画像

- [ ] 合成データで撮ったか（個人情報・実データが写っていないか）
- [ ] `alt` が画像の内容で、「画像」「スクリーンショット」と書いていないか
- [ ] 直後にキャプションがあり、枠で囲んだものを名前で書いているか
- [ ] `<img>` に `width` / `height` があり、遅延読み込みにしていないか

- [ ] `lg` 未満で目次が本文の上に畳まれているか
- [ ] 本文の末尾に前後のページへのリンクがあるか
- [ ] マニュアルのページを権限で隠していないか。要る権限をページの冒頭に書いたか
